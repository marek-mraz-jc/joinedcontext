## Token endpoint scope behaviour (OIDC, beside the admin rows)

| # | Grant | Behaviour, as Keycloak 26.8 | Test |
|---|---|---|---|
| T1 | `authorization_code`, `refresh_token` | An optional scope with `include.in.token.scope=false` (`gateway-hub`) asked at `/authorize` keeps its protocol mappers at the code exchange and on every refresh (`aud: mcp-hub` for `portal-api`, as `client_credentials` gives); the `scope` claim leaves it out as before. An optional scope not linked to the client is `invalid_scope` at `/authorize` (`endpoint:*` and an unlinked `endpoint:{slug}` included). A mapper scope the client lost between `/authorize` and the token request is dropped, as `TokenManager.getRequestedClientScopes` drops it; a refresh adds no scope it asks for. | `server/tests/portal_contract.rs::an_optional_scope_outside_the_scope_claim_keeps_its_mappers_in_the_code_flow` |
| T2 | every grant | A client attribute `access.token.signed.response.alg` or `id.token.signed.response.alg` gets a token of exactly that algorithm. Keycloak creates a key for a requested algorithm it lacks (measured for ES512 only, `evidence/jc-edge-design-2/results/alg-probe-keycloak.txt`; PS* not probed); kaisatsu generates a missing ES256, RS256 or EdDSA key and refuses every other algorithm: `400` naming the client and the attribute at an admin client write (rows 36, 37), `partialImport` (row 4) and realm import, `500 server_error` naming the client (never a key) at the token endpoint for a client stored before the check. An empty attribute means the realm default, which alone may fall back to another active key. | `server/tests/oidc_errors.rs::a_pinned_algorithm_without_a_key_is_refused`, `::a_pinned_es256_rs256_eddsa_key_is_generated`, `::an_empty_algorithm_attribute_uses_the_realm_default`, `admin/tests/compat_tests.rs::a_client_write_pinning_an_algorithm_the_realm_cannot_sign_is_refused`, `import/tests/import_errors.rs::a_client_pinning_an_algorithm_the_realm_cannot_sign_is_refused` |
| T3 | `refresh_token` | Reuse, as Keycloak 26.8 with `refreshTokenMaxReuse` 0: a handle presented after it was rotated away, or by a parallel request that lost the rotation, answers `invalid_grant` and revokes its token family (its refresh and access tokens: inactive at introspection, refused at userinfo and token exchange); the SSO session stays, so the client signs the person in again without a password (Keycloak removes the token family and the client session and keeps the IdP session). One `REFRESH_TOKEN_ERROR` event (`error: refresh_token_reuse`) and `kaisatsu_refresh_token_reuse_total{reason}` per reuse. kaisatsu always rotates: `revokeRefreshToken` and `refreshTokenMaxReuse` are imported and not read. | `server/tests/refresh_reuse.rs` (memory and PostgreSQL) |
