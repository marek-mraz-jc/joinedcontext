# JoinedContext (`jc`) Monorepo Layout

Every module in the `jc/` Cargo workspace is a product of its own (PART C §2.1, §9.7):
- It has its own crate(s), its own standalone binary, its own HTTP/gRPC API, and its own PostgreSQL schema (`STORE-01`).
- It can be deployed alone with only PostgreSQL and an object store, scaled independently (`jc run --modules <list>`), or composed into the single all-in-one `jc` binary that fits within the 2 GiB memory budget.
- Every module's source, tests, and interface crates stay at or under 700,000 tokens (`MOD-06`), with individual crates under 250,000 tokens so a single crate plus its dependencies' public API fits one agent context.

## Dependency & Isolation Rules

1. **API-only inter-module communication:** Modules talk to each other **only** over their documented HTTP/gRPC API (`jc-<module>-api` trait with in-process and tonic gRPC adapters) or shared foundational library crates (`jc-core` types, `jc-auth` token checks).
2. **Strict schema ownership:** No module ever reads or writes another module's PostgreSQL schema. Each module connects using its own NOLOGIN database role (`jc_identity`, `jc_control`, `jc_data`, etc.) without `BYPASSRLS`.
3. **Universal tenancy key:** `OrgId` (128-bit opaque UUIDv7) is the first column of every primary key `PRIMARY KEY (org_id, id)` with `FORCE ROW LEVEL SECURITY` on `current_setting('jc.org', true)::uuid`, and prefixes every cache key, NATS subject, MQTT topic, and object-store path (`org/{OrgId}/...`).
4. **Crate acyclic hierarchy within `ekiben`:**
   - `ekiben-bloblang` depends on no internal crates and performs no async I/O (embeddable in Portal mapping preview and App SDK).
   - `ekiben-core` depends on `ekiben-bloblang`.
   - `ekiben-processors`, `ekiben-io-http`, `ekiben-io-file`, and `ekiben-io-nats` depend on `ekiben-core` (and `ekiben-bloblang`), never on each other's internals.
   - `ekiben-server` wires the registries and exposes the streams HTTP API, scheduler, and `ekiben` CLI binary.
